Pengembangan Web Full-Stack

Warmindo25

Membangun sistem pemesanan makanan berbasis web untuk Warmindo 25. Pelanggan memindai QR Code di meja untuk melihat menu dan memesan langsung dari ponsel. Algoritma Dynamic Estimated Time of Arrival (ETA) menghitung estimasi waktu tunggu berdasarkan kapasitas dapur, sehingga pelanggan tahu kapan pesanan mereka siap.

JavaScriptPHPMySQLphpMyAdminCSSQR Code

Database: MySQL (MariaDB di XAMPP) dengan 10 tabel berelasi, dikelola lewat phpMyAdmin dan diakses dari PHP.

Analisis Bisnis: Warmindo25
1. Latar Belakang & Masalah Bisnis

Warmindo 25 melayani pesanan secara manual: pelanggan memanggil pelayan atau datang ke kasir, lalu pesanan dicatat dan diteruskan ke dapur. Pada jam ramai, proses ini rawan antrean panjang, kesalahan pencatatan, pesanan terlewat, dan pelanggan tidak mendapat kepastian waktu tunggu.

  • Pencatatan pesanan manual memakan waktu dan rentan salah tulis.
  • Dapur tidak memiliki gambaran beban kerja yang terukur.
  • Pelanggan tidak tahu berapa lama harus menunggu, sehingga menurunkan kepuasan.
  • Pemilik sulit merekap penjualan dan menu terlaris secara cepat.
2. Tujuan Bisnis
  • Mempercepat dan merapikan proses pemesanan serta mengurangi kesalahan pencatatan.
  • Memberi kepastian waktu tunggu kepada pelanggan melalui estimasi yang dinamis.
  • Membantu dapur mengatur antrean sesuai kapasitas.
  • Menyediakan data transaksi yang rapi sebagai dasar evaluasi usaha.
3. Pemangku Kepentingan (Stakeholder)
PihakPeran & Kebutuhan
PelangganMemesan dengan mudah, melihat menu, dan mengetahui estimasi waktu tunggu.
Kasir / PelayanMenerima dan memantau pesanan tanpa pencatatan manual.
DapurMelihat antrean pesanan dan memperbarui status pengerjaan.
Pemilik / AdminMengelola menu dan harga, serta memantau rekap pesanan.
4. Analisis Proses: Kondisi Saat Ini vs Solusi
Kondisi Saat Ini (As-Is)Solusi (To-Be)

Pesanan ditulis tangan lalu diteruskan ke dapur.Pesanan masuk otomatis ke sistem dan tampil di dapur.

Rekap penjualan dihitung manual.Data pesanan tersimpan di basis data dan siap direkap.
5. Kebutuhan Fungsional
  • Identifikasi meja melalui QR Code.
  • Menampilkan daftar menu, kategori, harga, dan keranjang pesanan.
  • Pengiriman pesanan dan pelacakan status (diterima, diproses, siap).
  • Perhitungan estimasi waktu tunggu secara dinamis.
  • Pengelolaan menu dan pesanan oleh admin / dapur.
6. Kebutuhan Non-Fungsional
  • Tampilan responsif dan nyaman dipakai di ponsel.
  • Antarmuka sederhana agar pelanggan dari berbagai usia dapat memakainya tanpa pelatihan.
  • Respons sistem cepat saat jam ramai dan data pesanan tersimpan dengan aman.
7. Logika Dynamic ETA

Estimasi waktu tunggu tidak dibuat tetap. Sistem mempertimbangkan jumlah pesanan yang sedang antre, waktu pengerjaan tiap menu, dan kapasitas dapur pada saat itu. Semakin padat antrean, semakin panjang estimasi yang ditampilkan, sehingga angka yang diberikan lebih realistis dibandingkan perkiraan manual.

8. Metode Pengembangan

Sistem dikembangkan dengan metode Waterfall melalui tahap analisis kebutuhan, perancangan sistem, implementasi, pengujian, dan pemeliharaan. Pendekatan ini dipilih karena kebutuhan sistem relatif jelas dan terdefinisi sejak awal.

9. Nilai & Manfaat Bisnis
  • Proses pemesanan lebih cepat dan minim kesalahan.
  • Kepuasan pelanggan meningkat karena ada kepastian waktu tunggu.
  • Beban kerja kasir dan pelayan berkurang.
  • Pemilik memperoleh data pesanan yang terstruktur untuk evaluasi dan pengambilan keputusan.
10. Indikator Keberhasilan
  • Berkurangnya kesalahan pencatatan pesanan.
  • Berkurangnya waktu dari pesanan masuk hingga sampai ke dapur.
  • Selisih antara estimasi dan waktu penyajian sebenarnya semakin kecil.
  • Umpan balik pelanggan terkait kemudahan pemesanan.

4. Data Pendukung Dynamic ETA
  • Tabel orders menyimpan eta_minutes (estimasi waktu tunggu), cooking_start dan cooking_finish (waktu mulai dan selesai memasak), serta actual_minutes (lama pengerjaan sebenarnya).
  • Kolom eta_result (Tepat Waktu, Lebih Cepat, atau Terlambat) membandingkan estimasi dengan kenyataan, sehingga akurasi algoritma dapat dievaluasi.
  • Tabel owner_statistics menyediakan tempat rekap harian: pendapatan, jumlah pesanan, rata-rata ETA, dan jumlah pesanan tepat waktu, terlambat, atau lebih cepat.
  • Status pesanan (Menunggu Pembayaran, Pending, Diproses, Disajikan, Selesai) dibatasi dengan ENUM agar nilainya selalu valid.
5. Contoh Query SQL

JOIN: rincian pesanan yang sedang diproses beserta nomor mejanya, untuk antrean dapur.

SELECT o.id, t.nomor_meja, m.nama_menu, oi.quantity, oi.subtotal
FROM orders o
JOIN tables t       ON t.id = o.table_id
JOIN order_items oi ON oi.order_id = o.id
JOIN menu m         ON m.id = oi.menu_id
WHERE o.status = 'Diproses'
ORDER BY o.order_time;

GROUP BY: rekap pendapatan harian.

SELECT DATE(order_time) AS tanggal,
       COUNT(*) AS total_order,
       SUM(total) AS pendapatan
FROM orders
WHERE status = 'Selesai'
GROUP BY DATE(order_time)
ORDER BY tanggal DESC;

Menu terlaris: lima menu dengan jumlah terjual terbanyak.

SELECT m.nama_menu, SUM(oi.quantity) AS terjual
FROM order_items oi
JOIN menu m ON m.id = oi.menu_id
GROUP BY m.id, m.nama_menu
ORDER BY terjual DESC
LIMIT 5;

Evaluasi ETA: perbandingan hasil estimasi dengan lama pengerjaan sebenarnya.

SELECT eta_result, COUNT(*) AS jumlah,
       AVG(actual_minutes) AS rata_menit
FROM orders
WHERE eta_result IS NOT NULL
GROUP BY eta_result;
6. Fungsi Basis Data dalam Sistem
  • Menjadi sumber data bersama bagi pelanggan, dapur, kasir, dan pemilik.
  • Menyimpan jejak waktu pesanan, mulai masuk, dimasak, hingga selesai, sebagai bahan perhitungan dan evaluasi Dynamic ETA.
  • Menghasilkan struk bernomor dan rekap penjualan tanpa pencatatan manual.

  • Analisis masih bersifat deskriptif; belum menjelaskan penyebab perbedaan antarnegara.
  • Dapat dikembangkan dengan tambahan variabel, analisis tren, atau dasbor interaktif.
7. Keterampilan yang Terasah

Pembersihan data, pemahaman kualitas data, pemilihan jenis visualisasi yang tepat, dan penyampaian hasil analisis secara ringkas.

Analisis Bisnis: Aplikasi Pengaduan Masyarakat
1. Latar Belakang & Masalah Bisnis

Pengaduan masyarakat yang disampaikan secara lisan atau tertulis di atas kertas sulit dilacak, mudah hilang, dan tidak memberi kepastian tindak lanjut. Pihak pengelola pun kesulitan merekap jumlah laporan, jenis masalah, dan status penanganannya.

  • Laporan tidak tercatat rapi dan sulit dicari kembali.
  • Pelapor tidak mengetahui status laporannya.
  • Pengelola tidak memiliki data terpusat untuk evaluasi.
2. Tujuan Bisnis
  • Menyediakan kanal pengaduan yang mudah diakses kapan saja.
  • Mencatat seluruh laporan secara terstruktur dalam basis data.
  • Memberi transparansi status laporan kepada pelapor.
  • Mempermudah pengelola meninjau dan menindaklanjuti laporan.

  1. Pengguna mendaftar dan login.

  3. Laporan tersimpan di basis data dan muncul pada riwayat pengguna.
  4. Pengelola meninjau laporan dan menindaklanjutinya.
  5. Pengguna memantau perkembangan melalui halaman riwayat.
6. Kebutuhan Fungsional
  • Registrasi, login, dan logout pengguna (autentikasi).
  • Formulir pengaduan yang terstruktur.
  • Dasbor ringkasan, riwayat pengaduan, dan detail riwayat.
  • Pengelolaan profil pengguna.
  • Penyimpanan seluruh data ke basis data.
7. Kebutuhan Non-Fungsional
  • Keamanan akun: hanya pengguna terautentikasi yang dapat mengakses data laporannya.
  • Tampilan sederhana dan mudah dipahami masyarakat umum.

  • Setiap laporan memiliki status yang dapat dipantau.
9. Nilai & Manfaat Bisnis
  • Layanan pengaduan lebih mudah diakses dan transparan.
  • Data laporan terdokumentasi sehingga tidak mudah hilang.

  • Data dapat menjadi dasar evaluasi dan perbaikan layanan.
10. Indikator Keberhasilan
  • Jumlah laporan yang berhasil tercatat dan dapat ditelusuri.
  • Waktu dari laporan masuk hingga ditinjau pengelola.
  • Kemudahan pengguna menyelesaikan alur pengaduan pada saat uji coba.

Penjelasan Database: Aplikasi Pengaduan Masyarakat
1. Gambaran Basis Data

Seluruh laporan, akun, tanggapan, dan riwayat status disimpan di basis data relasional MySQL dengan lima tabel yang saling berhubungan. Struktur dibuat melalui satu berkas SQL yang dapat diimpor ulang di phpMyAdmin, sehingga basis data mudah dipasang dan dipulihkan.

KomponenYang Digunakan

PengelolaanphpMyAdmin 5.2 dan SQL
Akses dari aplikasiPHP 8 (PDO) dengan prepared statement
PerancanganERD dan flowchart alur pengaduan
2. Kebutuhan Data
  • Akun dengan peran berbeda: masyarakat, petugas, dan admin.
  • Laporan lengkap dengan kategori, lokasi, tanggal kejadian, foto, dan status.
  • Tanggapan petugas atas setiap laporan.
  • Catatan setiap perubahan status agar laporan dapat ditelusuri dari masuk hingga selesai.
3. Struktur Tabel & Relasi
TabelFungsiKunci & Relasi
usersAkun masyarakat, petugas, dan adminPK id; UNIQUE email dan nik
kategoriJenis masalah yang dilaporkanPK id; UNIQUE nama
pengaduanData laporan, status, dan kode tiketPK id; UNIQUE kode_tiket; FK user_id ke users, kategori_id ke kategori, petugas_id ke users
tanggapanBalasan petugas pada laporanPK id; FK pengaduan_id ke pengaduan, petugas_id ke users
riwayat_statusJejak perubahan status laporanPK id; FK pengaduan_id ke pengaduan, diubah_oleh ke users
4. Aturan Integritas Data
  • CASCADE: laporan ikut terhapus bersama akun pelapornya.
  • RESTRICT: kategori yang masih dipakai laporan tidak dapat dihapus.
  • SET NULL: laporan tetap ada saat akun petugas dihapus.
  • ENUM dan UNIQUE: status dan peran hanya menerima nilai yang diizinkan, dan email, NIK, serta kode tiket tidak boleh ganda.
  • Index pada kolom status dan pengguna agar pencarian tetap cepat.
5. Contoh Query SQL

JOIN: antrean laporan yang menunggu verifikasi, terlama lebih dulu.

SELECT p.kode_tiket, p.judul, k.nama AS kategori,
       u.nama AS pelapor, p.created_at
FROM pengaduan p
JOIN users u    ON u.id = p.user_id
JOIN kategori k ON k.id = p.kategori_id
WHERE p.status = 'menunggu'
ORDER BY p.created_at ASC;

UPDATE aman: status hanya berubah jika masih sama seperti saat halaman dibuka, lalu dicatat ke riwayat.

UPDATE pengaduan
SET status = 'diverifikasi', updated_at = NOW()
WHERE id = ? AND status = 'menunggu';

INSERT INTO riwayat_status (pengaduan_id, status, catatan, diubah_oleh)
VALUES (?, 'diverifikasi', 'Laporan terverifikasi oleh petugas', ?);

GROUP BY: rekap jumlah laporan per kategori untuk dasbor.

SELECT k.nama, COUNT(p.id) AS jumlah
FROM kategori k
LEFT JOIN pengaduan p ON p.kategori_id = k.id
GROUP BY k.id, k.nama
ORDER BY jumlah DESC;
6. Keamanan Data
  • Password disimpan sebagai hash (bcrypt), bukan teks asli.
  • Prepared statement pada semua query untuk mencegah SQL injection.
  • Setiap pengguna hanya dapat membuka laporannya sendiri, dan halaman petugas dibatasi berdasarkan peran.
7. Dokumentasi & Penelusuran

Setiap laporan memiliki kode tiket dan riwayat status bertanda waktu di tabel riwayat_status. Dengan begitu perkembangan laporan terdokumentasi dan dapat dilacak oleh pelapor maupun petugas.
